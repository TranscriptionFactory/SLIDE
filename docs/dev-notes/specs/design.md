# Design: `slide-rs` — Pure Rust Port of loveslide

## Context

`loveslide` implements SLIDE (Statistical Latent Inference for Discovery and Explanation). The pipeline is:

1. Accept feature matrix X (n x p) and response y (n,).
2. LOVE decomposition: find loading matrix A (p x k) and latent scores Z (n x k) such that X ≈ A @ Z + E, with a covariance structure on Z enforced via an SDP.
3. Knockoff filter with voting: generate knockoff copies Z_tilde, compute lasso-path-based knockoff statistics W for each latent factor, apply the knockoff threshold at a target FDR, run across multiple random seeds and retain factors that survive a vote fraction.
4. Interaction detection: test pairs of significant factors for multiplicative effects on y.
5. Score: report held-out prediction metrics.

The current implementation delegates steps 2-5 to R via `rpy2`. `slide-rs` re-implements every step in Rust with numerical choices that reproduce R reference output.

The canonical correctness target is the R `SLIDE` package (the archived reference, not the Python wrapper). Test fixtures are generated by running the R implementation on synthetic and real datasets and saving its outputs. `slide-rs` integration tests load those fixtures and assert numerical agreement within tolerance.

## Goals / Non-Goals

**Goals**

- Numerical correctness: outputs match R reference within 1e-6 relative tolerance on synthetic benchmarks and within accepted floating-point variation on real datasets. Note: `specs/specs/correctness/spec.md` is the authoritative source for per-component tolerances (e.g., 1e-14 for EstC, 1e-12 for estOmega); the 1e-6 stated here is a general bound that individual components may tighten.
- Zero-copy matrix operations: avoid unnecessary allocation in hot paths; use views where the borrow checker allows.
- Safe parallelism: data-parallel operations (bootstrap resampling, cross-validation folds, knockoff seed sweeps) use rayon without unsafe code.
- No runtime dependencies on R or Python: the compiled binary and library crate are self-contained.
- Deterministic output: given the same inputs and the same RNG seed, `slide-rs` produces identical results across platforms with the same IEEE 754 floating-point behavior.
- Reproducibility against R: MT19937 seeding matches R's `set.seed()` / `.Random.seed` so that fixture generation and Rust execution can use the same seed and produce the same random draws.

**Non-Goals**

- Graphical user interface or interactive dashboard.
- Web API or HTTP server.
- Streaming or online updates to a fitted model.
- Real-time processing or low-latency inference.
- GPU acceleration.
- Support for sparse X matrices in the initial release.
- Automatic differentiation or gradient-based optimization.
- PyO3 Python bindings (post-port deliverable; tracked separately).

## Decisions

### Crate structure

`slide-rs` is a Cargo workspace. Sub-crates map to pipeline stages and are independently testable:

```
slide-rs/
  Cargo.toml          # workspace manifest
  crates/
    love/             # LOVE decomposition and SDP covariance step
    knockoff/         # knockoff generation and W statistic
    slide/            # pipeline orchestrator, interaction detection
    cv/               # cross-validation wrapper
    score/            # prediction metrics
    sdp/              # SDP solver (clarabel wrapper or DSDP port)
    glmnet/           # coordinate-descent lasso
    data-io/          # matrix I/O and model serialization
    slide-cli/        # binary crate; thin CLI over slide::Pipeline
```

Public types (matrix newtype wrappers, config structs, error enums) live in a `slide-types` crate that all others depend on. This prevents circular dependencies.

**Rationale.** Keeping SDP and lasso as independent crates lets them be swapped or upgraded without touching pipeline logic. The CLI crate has no library logic; it is a thin argument parser over `slide::Pipeline`.

### Matrix library

`nalgebra` is used for all linear algebra operations that require matrix decompositions (eigendecomposition, SVD, Cholesky). `ndarray` is used for array slicing, broadcasting, and operations that benefit from its NumPy-like indexing. The two are bridged via the `nalgebra-ndarray` or manual `as_slice` conversions at sub-crate boundaries.

**Rationale.** `nalgebra` has mature LAPACK bindings (`nalgebra-lapack`) that call the same BLAS/LAPACK routines as R's Matrix package, minimizing eigendecomposition divergence. `ndarray` is more ergonomic for the data-wrangling steps (fold splits, column selection) that do not need decomposition.

### SDP solver

The `clarabel` crate (pure Rust interior-point solver for conic programs, MIT license) is used for the LOVE covariance SDP. `clarabel` accepts standard-form conic constraints and returns dual variables needed for the knockoff SDP step.

**Rationale.** `clarabel` is actively maintained, has no C dependencies, and has been validated against CVXR's default solver on several SDP benchmarks. A DSDP port was considered but would require porting ~8 kLOC of C; clarabel reduces that to a thin problem-formulation layer.

**Acceptance criterion.** The SDP solution must agree with CVXR/SCS output on LOVE covariance problems to within 1e-4 primal/dual gap before this decision is considered validated.

### Lasso (glmnet-stats)

Coordinate descent matching glmnet's conventions:

- Lambda grid: `nlambda = 250` points on a log scale from `lambda_max` down to `lambda_min_ratio * lambda_max` (ratio = 1e-4 for n > p, 1e-2 otherwise), matching glmnet defaults.
- Warm starts: solution at lambda[i] initializes the solver at lambda[i+1].
- Active-set cycling: only cycle over the active set after the first full pass that does not change the active set.
- Standardization: X columns are standardized before fitting; coefficients are un-standardized before return, matching glmnet's internal behavior.
- Convergence: coordinate-wise change threshold 1e-7, matching glmnet's `thresh` default.

**Rationale.** The knockoff W statistic is the difference in lasso entry points between original and knockoff variables. Any difference in the lambda grid or convergence criterion between glmnet and the Rust solver directly shifts W values, potentially changing which factors survive the knockoff threshold. Matching glmnet's exact schedule is therefore a correctness requirement, not a preference.

### RNG (MT19937)

The `mt19937` crate (or an equivalent pure-Rust Mersenne Twister implementation) is used for all random draws. Seeds are set to match R's `set.seed(n, kind="Mersenne-Twister")` behavior. A utility function `r_seed(n: u32) -> Mt19937Rng` encapsulates the seed initialization protocol so that fixture generation and Rust tests can use the same integer seed.

**Rationale.** Knockoff generation draws samples from a multivariate normal; the voting procedure runs across multiple seeds. Using the same RNG and seed protocol as R allows fixtures to be generated with `set.seed(42)` in R and verified with `r_seed(42)` in Rust.

**Note.** R's Mersenne Twister state after `set.seed(n)` uses a specific initialization loop that differs from simply seeding MT19937 with n. The `r_seed` utility must replicate that initialization loop, not just pass n directly to the MT state array.

### Error handling

`thiserror` for library error types (one enum per sub-crate, variants for each failure mode). `anyhow` in the CLI crate and in test code where context chaining is useful. No `unwrap` or `expect` in library code; every fallible call returns `Result`.

**Rationale.** `thiserror` keeps error types structured and matchable by downstream callers. `anyhow` is appropriate at the application boundary where human-readable context is more useful than matchable variants.

### Parallelism

`rayon` is used for:

- Cross-validation: folds run in parallel via `par_iter` over fold indices.
- Knockoff seed sweep: each seed produces an independent knockoff sample; these run in parallel via `par_iter` over seeds.
- Bootstrap resampling (if used in scoring): parallel over resamples.

Single-sample matrix operations (e.g., a single SDP solve) are not parallelized internally; rayon's thread pool handles coarse-grained parallelism at the pipeline level.

**Rationale.** The seed sweep is the dominant runtime cost. Parallelizing it with rayon requires no `unsafe` and scales linearly with available cores.

### Testing strategy

- **Unit tests**: inline `#[test]` for pure functions (lambda grid construction, coordinate-descent steps, MT19937 seed initialization).
- **Property-based tests**: `proptest` for numerical invariants (e.g., SDP solution satisfies PSD constraint, lasso solution is sparse when lambda is large, knockoff matrix has correct correlation structure).
- **Integration / correctness tests**: fixtures generated by R and Python reference implementations, stored under `tests/fixtures/`. Each fixture is a pair of input files and expected output files. Integration tests load a fixture, run the corresponding `slide-rs` sub-crate, and assert agreement within tolerance.
- **Benchmarks**: `criterion` for hot paths (SDP solve, lasso path, LOVE decomposition). Benchmarks are not run in CI by default; they are run manually before release.

Fixture generation scripts live in `tests/fixtures/generate/` and require R and Python environments. Generated fixture files are committed to the repository so CI has no R dependency.

## Risks / Trade-offs

**Eigendecomposition differences (LAPACK version sensitivity).** LOVE decomposition relies on eigendecomposition of a covariance matrix. Different LAPACK versions can return eigenvectors with flipped signs or reordered eigenvalues when eigenvalues are near-degenerate. The integration tests must use sign-normalized eigenvectors (flip each eigenvector so its largest-magnitude component is positive) before comparing to fixtures, and fixtures must be generated with the same normalization applied to R output. Without this normalization, tests will fail on clusters with different LAPACK builds even when the decomposition is numerically correct.

**SDP solver convergence differences.** `clarabel` and CVXR/SCS may converge to different feasible points for the LOVE covariance SDP when the problem is near the boundary of feasibility (e.g., very small eigenvalues). Downstream knockoff statistics are sensitive to the SDP solution because it determines the conditional covariance of the knockoff variables. If agreement with R fixtures cannot be achieved to 1e-4 on real datasets, a tolerance relaxation or a problem-conditioning step (adding a small diagonal perturbation) may be needed. Tolerance relaxation is a last resort; the thresholds defined in `specs/specs/correctness/spec.md` take precedence, and any relaxation must be justified and documented. This is the highest-risk decision in the design.

**Lasso path sensitivity to lambda grid.** Even with matching glmnet conventions, floating-point differences in the lambda grid endpoints (due to different max-absolute-correlation computations) can shift entry points for low-signal variables. The knockoff W statistic for variables that enter near the bottom of the lambda grid is therefore sensitive to small numerical differences. The acceptance criterion for the lasso sub-crate is agreement on W statistics, not on individual coefficient paths, and the tolerance should be calibrated on synthetic datasets with known ground truth rather than on the magnitude of W values alone.

**MT19937 seed initialization.** R's `set.seed` initialization loop uses a specific polynomial recurrence to fill the MT state array. If the Rust `r_seed` utility does not replicate that loop exactly, knockoff draws will differ from R fixtures even with matching lambda grids and SDP solutions. This is a subtle but mechanical risk: the R source code for the initialization loop is public and can be transcribed directly.

**Build time.** A workspace with eight sub-crates and heavy dependencies (`nalgebra`, `ndarray`, `clarabel`, `rayon`, `proptest`, `criterion`) will have a long cold-build time. Module-level `[profile.dev]` settings (opt-level = 1 for dependencies) and `sccache` in CI should keep incremental builds under two minutes.
